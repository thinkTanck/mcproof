## What MCProof is

Standalone, deployed web app that red-teams an MCP-tool-using agent against the OWASP Top 10 for Agentic Applications (2026). **The competitive product: point your own MCP agent at us → live red-team it against the Core-7 → get a trustworthy report from a detector whose accuracy is *measured* (leakage-separated P/R).** Two access modes: a no-key **sample playback** (a constructed demonstration: real builder traces judged by the real frozen judge — the trailer) and **live red-teaming** (the tool).

**MCProof IS the MCP server; the user's agent connects TO us** ([ADR-0006](docs/adr/0006-mcpwn-is-the-mcp-server.md)). Per run we host an MCP endpoint that serves the attack's `Environment` — the Core-7 tools, some deliberately over-broad or mis-described, plus seeded memory and prompts — and we record every `tools/call` the agent chooses to make into the `Trace`. **You cannot poison what you do not serve:** ASI01/02/04/05/06 are all staged through the tool surface, so serving it is what makes them stageable at all. `Scenario.taskGoal` is delivered **out of band** (a published MCP prompt preferred, paste as fallback), because MCP has no server-to-agent "here is your goal" message. **`agent_reasoning` is not observable** from the server side and is never synthesized; `task_complete` is **inferred** and labelled as such.

The user still brings the agent and pays its inference; **they no longer hand us its endpoint or key** — we never call their agent, so we hold no credential of theirs. The **judge is the fixed, validated, operator-provided detector — LOCKED** and never user-swappable (the measured accuracy only holds for the validated judge config). Live runs are **gated** (email-OTP sign-in + a **per-account LIFETIME free allowance**, default ~3 runs total, NOT per day) with a cheap validated judge, so operator judge cost stays a few cents per run ([ADR-0007](docs/adr/0007-access-and-cost-model.md)). Hero: the attack replay. Supporting: per-model robustness leaderboard + engineer-ready fix reports.

## Stack

- Next.js (App Router) + TypeScript, deployed on Vercel. **Production is `https://mcproof.dev` — the canonical URL**, and the origin page metadata resolves against (`NEXT_PUBLIC_SITE_URL`). **Issued run endpoints are built on `MCP_ENDPOINT_ORIGIN`** (env, optional): unset, it is the site origin; set, it must be a bare https origin, and an invalid value falls back to the site origin with a logged warning (`getMcpEndpointOrigin()` in `src/config/env.ts`). It exists so the endpoint saved in the agent's MCP config can live on a neutral host that names no product. The Vercel-generated `*.vercel.app` domain still resolves but is never the stated URL.
- UI: Tailwind + shadcn/ui on the **Base UI** engine (not Radix — unmaintained). DTCG two-tier design tokens (primitives → semantic aliases) → CSS variables → Tailwind.
- Persistence: **Supabase Postgres** behind a repository port — **exactly one run store**, `RunRepository` in `src/data/run-repository.ts`, keyed `(userId, uuid)` and owner-scoped by RLS; a Supabase adapter (via the Supabase JS client, not a raw `DATABASE_URL`) for prod and an in-memory adapter for tests/offline. **Reads and writes use different clients (2026-10-13, security lane S1a).** A signed-in user READS their own rows through their own cookie session under `runs_select_own`: `getRunRepository()` and `getDiscardedRunStore()` hand out `SupabaseRunReader`, which has no insert on it at all. Every WRITE (a judged result, a discard marker) is made by ONE server-only module, `src/runs/run-writes.ts`, on the SERVICE-ROLE client, and `SupabaseRunRepository` (the reader plus the two inserts) is constructed nowhere else (`tests/unit/runs/run-write-paths.guard.test.ts`). Runs are inserted and never updated or deleted. **The database says the same (migration `0004_runs_server_only_writes.sql`, security lane S1b):** `public.runs` carries ONE policy, `runs_select_own`, for `authenticated` only, on `user_id = (select auth.uid())`; `authenticated` holds SELECT and nothing else, `anon` holds nothing, and only the service role can insert, update, delete or truncate. The earlier second store (`src/persistence/*`, keyed by bare `runId`, with a provider-agnostic `DATABASE_URL` postgres adapter) was **superseded and deleted** — two semantically incompatible stores meant a live run could be wired to the wrong one.
- Auth: **Supabase Auth** — **emailed one-time code (OTP)** sign-in (optional GitHub/Google OAuth) — gates live runs. **Code-only by design: the email carries a code and NO clickable link**, because a link and a typed code share one token, so a corporate scanner that pre-fetches the URL spends it and breaks the code too. Two steps in one browser: `requestEmailCode` (`signInWithOtp`) then `verifyEmailCode` (`verifyOtp`). **`/auth/callback` exists for GitHub OAuth only** and is the sole remaining PKCE consumer. **Every `next` return path goes through ONE guard, `sanitizeNext` in `src/lib/auth/next.ts` (2026-10-13):** the sign-in action, the callback route and the shell's sign-in link all use it, a refused value becomes `/account`, and the callback builds its redirect with `new URL(path, origin)` and checks the origin again, never by joining text (origin plus `@host` is another site). The guard refuses anything that is not a single-slash relative path, a backslash, any control character (a URL parser deletes tabs and newlines, so slash, tab, slash is a host), a path that collapses to a leading double slash, and anything over 2048 characters. **The send must go through a non-PKCE client** (`@supabase/ssr` forces `flowType: "pkce"`, under which GoTrue stores a flow-state code instead of the OTP hash and no emailed code can ever verify; `createOtpSenderSupabase()` in `src/lib/supabase/server.ts` carries the full trace). **The code length is a Supabase project setting (6 to 10), never a hardcoded constant** — it is mirrored in `NEXT_PUBLIC_EMAIL_OTP_LENGTH` and every human-visible mention derives from it. Config is env-only, and these are the ONLY names any code reads (`src/config/env.ts` is the single accessor): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` (public — the `NEXT_PUBLIC_` prefix is REQUIRED so the browser auth client can read them, and they inline at BUILD time), `SUPABASE_SERVICE_ROLE_KEY` (secret, **server-only**, read at runtime), and `DATABASE_URL`, which is **TOOLING-ONLY — no application code reads or validates it** (it carries the database password `npm run db:link` prompts for; the run store reaches Postgres through the Supabase JS client). Secrets never logged, never persisted in plaintext.
- External access behind domain-named ports: `JudgeModelPort`, `McpTargetPort` — HTTP adapters validate their own creds lazily, so the offline app boots with none. **Under [ADR-0006](docs/adr/0006-mcpwn-is-the-mcp-server.md) the live agent path is INBOUND** (module 1 hosts the MCP server the agent connects to); `McpTargetPort` keeps the narrower job of probing a target MCP *server* (the ASI02 / ASI05 surfaces) and supplying the shared transport / JSON-RPC / Zod / retry layer.

## UI & design

- **The design is the DEFAULT reference, not immutable.** [`design-review/MCPwn Sentinel v2.dc.html`](design-review/) is the **Wave C reference** for screens, layout, copy, states, and mobile. It was designed in Claude Design (that role is complete). We implement it in code, where Impeccable's method both works on it and measures it. It is the default we start from, **not a frozen artifact**: when Impeccable flags one of its moves, the finding is adjudicated (kept with a documented reason, or surfaced as a proposed change for sign-off), never overwritten by reflex and never auto-vetoed. See [ADR-0004](docs/adr/0004-design-frozen-and-impeccable-as-craft-gate.md).
- **THE PRINCIPLE — the design is the default reference; token roles DESCRIBE it, they do not silently redesign it.** If a *token role* and the design disagree, the design is the default and the role is re-examined. (Two spec errors proved this: a 65–75ch role-level measure cap produced dead side-margins by fighting the design's own columns, and pinning DISPLAY to mono rewrote the design's sans numerals. Both were "good typography" overruling the actual design.) Impeccable's *design* findings are different in kind: they may legitimately propose changing a design move. A flag becomes a **proposed change surfaced for sign-off** with the finding and our reason, not a unilateral overwrite and not an automatic veto. See ADR-0004.
- **The THREE-ROLE type model** (built + measured; DTCG roles in `src/app/globals.css`, locked by `tests/unit/app/tokens.test.tsx`):
  - **READING** — sans · 17 body / 18 lead / 20 · 28 · `clamp(32px, 5cqi, 44px)` · **every sentence a human reads**.
  - **INSTRUMENT** — mono · 12–13px · **line-height 1.5** · **telemetry only**: labels, chips, metadata, cues, column/row headers.
  - **DISPLAY** — **family per the frozen design** · 15 / 20 / 28 / 40 · values that **are** the focus (leaderboard cell values + OVERALL, hero stats).
  - Hard rules: **prose NEVER wears an INSTRUMENT role** (a blocking review failure); roles stay **measurably** distinct (`--display-sm` and `--reading-body` both above the INSTRUMENT ceiling); headline sizing is **`cqi`, never `vw`** (the column tracks the command deck, not the viewport); a tri-state **band colour overrides DISPLAY at zero specificity** via `:where()`; the READING *role* pins **no measure** (the design owns layout width). **Body paragraphs opt in to the `measure` utility** (`src/app/globals.css`): a fixed 34rem, about 66 characters on a typical line, left-aligned so prose and the copy-out boxes share one left edge. It is rem and not `ch` on purpose: `ch` is the width of the digit zero, Geist's zero is far wider than its average letter, and the `max-w-[68ch]` it replaced held about 97 characters a line. Headings, labels, readouts, copy-out boxes and grids never take it. Measured in `tests/e2e/reading-measure.spec.ts` (typical line at or under 75, no line over 80, at 1280px in both the loaded and the fallback font).
- **Small text that can wrap has a line-height of 1.5 (2026-10-10, owner-approved; WCAG 1.4.12).** A mono label that holds one line on a desk wraps on a phone, and at the old 1.2 to 1.3 two wrapped lines sat on top of each other. `--instrument-line` is 1.5 and **every INSTRUMENT class takes it by default** (`.instrument`, `.instrument-faint`, `.readout`, `.micro-label`), so a new label is right without anyone asking. **A control that holds exactly ONE line and is sized by it** (a chip, a tag, a button, a bar readout) adds **`one-line`** beside the role class and keeps the old value (`--instrument-line-single: 1.3`, `--instrument-line-single-label: 1.2`), so the header, the run bar, buttons and chips measure what they did. `one-line` never goes on anything that can wrap. Stacked small-text blocks take their gap from tokens as well: `--instrument-stack` (12px) between blocks, `--instrument-stack-rows` (8px) between the rows of one list. Locked in `tests/unit/app/tokens.test.tsx`; measured in `tests/e2e/small-text-line-spacing.spec.ts`, which **runs in Chromium AND WebKit** (in WebKit it runs in the `webkit-test-styles` Playwright project, because it injects a test style tag; the `webkit` project runs the other specs listed in `WEBKIT_SPECS` in `playwright.config.ts` and nothing else) at 320 and 390 wide: every wrapped block under 16px is at 1.5 or more, and with the WCAG 1.4.12 text-spacing override forced on, nothing is clipped, spilled or drawn over its neighbour. The gap that spec once recorded as an annotation (at 320 in the fallback font the override pushed the mode chip 12 to 18px past the edge) is closed: the header lets the chip drop to a second row, and the spec asserts no sideways scroll on every screen, the header included.
- **Enlarged text wraps, it is not cut off (2026-10-11, sweep S5; WCAG 1.4.4).** With the root font size at 200%, or every font size doubled in place, the run-bar and confirm buttons wrap their labels, the finished pair, the replay speed buttons and the sign-in pair wrap their rows, a file path and the verdict prompt break anywhere, and **the header is `min-h-(--header-h)` and may grow a second row for the mode chip**. At normal text size nothing moves: rows that have always reached a few pixels into their padding in the fallback font carry a small negative margin, and on a screen with a mode chip, below 480px, the header's two side paddings are room the row can take back (zero-basis `header-start` and `header-end` items that grow into what the row has left, the left one first), so a row that fits is drawn as it always was, a row that needs the whole screen gets it, and the header wraps only when the row is wider than the screen itself. **It never reaches past the screen (2026-10-13, #221):** the chip used to carry a negative margin of the padding plus 8px, which drew a row up to 8px past the edge before it would wrap, and in WebKit's fallback font at 360px the row is 365.5px, so the replay and the fix report scrolled sideways by 6px. **What hangs under the header reads its MEASURED height:** `HeaderHeightSync` (a small client island inside the header, a ResizeObserver) writes `--header-live-h` on the document root, and `--header-clear: var(--header-live-h, var(--header-h))` is what the pinned run bar's `top` and the document's `scroll-padding-top` use, so a taller header is never drawn over the bar. The two are equal at normal text size, so nothing shifts on load. The Connect column's scroll margin is `min(15rem, 50dvh)`, the same 15rem at normal size, so doubled rem cannot park a focused control below the fold. Measured in `tests/e2e/large-text-wraps.spec.ts` and `tests/e2e/run-bar-clears-header.spec.ts`, both in Chromium and WebKit at 320 and 390.
- **No text under 12px, and one focus ring (2026-10-12, UI audit batch A; WCAG 1.4.4, 2.4.7, 2.4.13).** `--text-floor` (12px, in px on purpose) is the smallest size any text is drawn at. Every role size is px and above it; the one step that followed the root font size, Tailwind's `text-xs` (0.75rem), is bridged in `@theme inline` as `max(0.75rem, var(--text-floor))`, so it still grows with an enlarged root and stops at the floor in a browser whose text size is turned down (it had dropped to 9px at a 12px root). A component that wants the floor writes `text-(length:--text-floor)`, never a literal `text-[12px]`. **The focus ring is ONE unlayered rule on the bare `:focus-visible`** (`src/app/globals.css`): `outline: var(--focus-ring-width) solid var(--focus-ring)` at `outline-offset: var(--focus-ring-place)`, an outline and nothing else, so it reaches every control without a tag list, cannot move the layout and survives forced-colors. Unlayered, so no utility can switch it off: **a component never styles its own ring** (no `focus:outline-none`, no `focus-visible:outline-*`, no `ring-*`). A control inside a box that clips (a replay terminal row, the step payload) adds **`focus-inside`**, which draws the same ring just inside the control (`--focus-ring-offset-inside`) so it is not cut off. It is deliberately *not* the full gate; **CI (which runs on every push) is the authoritative gate** (install → lint → typecheck → unit `--coverage` → build → e2e + axe → Lighthouse CWV → `impeccable detect` → `audit-ci`). **entering a code is limited too (2026-10-14, S1e)**: `verifyEmailCode` checks `otpVerifyRateLimiter`, 5 attempts per address and 20 per source per 15 minutes, before Supabase is asked anything, in the same `otp_rate_limit_hits` table under its own `verify-` key names so wrong codes never block a new code request, with the same one-sentence refusal; sign-in runs on the server, so Supabase's own per-IP verification limit is shared by every user and this is the per-user control), composed behind `checkLiveRunPreflight()` (`src/runs/preflight.ts`) and enforced before any agent or judge call, pausing down the `resolveLiveDetector()` null fail-safe (`src/detector/resolve.ts`). **The allowance is a TUNABLE DEFAULT read from config — never hardcode a numeral into copy**, and never state a specific free-run count until the enforcement actually honours it. **The allowance is ENFORCED through `checkLiveRunPreflight()`:** `checkLiveRunAllowance()` (`src/runs/allowance.ts`) counts a user's runs from **account creation** (lifetime, never a rolling window) via `countRunsSince`, compares that to `LIVE_RUN_ALLOWANCE` (env-only, default 3, `0` disables free live runs), and returns a decision carrying a typed `LiveRunAllowanceError` (`ALLOWANCE_EXHAUSTED`) instead of throwing; `describeLiveRunAllowance()` is the ONE place the number becomes words. Its caller is the live-run pipeline (`src/runs/live-run.ts`), which gates at both ends: before issuing a per-run token and again before the judge, failing closed on a refusal or an unreadable control. **RUNS ARE WRITTEN SERVER-SIDE ONLY (2026-10-13, security lane S1a; scan findings F1 and F2).** The finish and the discard used to insert through the caller's own session, which only works while `public.runs` lets its owner insert, and a grant the app relies on is one anybody holding the public anon key and their own session token can use directly against Supabase's REST API: a delete handed a spent lifetime allowance back and lowered the spend meter, an insert moved the global spend meter for everyone and planted a verdict nobody produced. The app no longer needs either grant. `src/runs/run-writes.ts` is the only code that inserts into `public.runs`, and because the service role skips RLS it makes the checks itself, before every write: **who** (the verified server session through `getUser()`, never `getSession()`, a header such as `x-shell-user-email`, a cookie read by hand or a request-body field; for the scheduled pass, which has no session, the owner on the run's own `live_runs` record), **whose** (the session account must be the owner that record names, and so must the id the caller passed, which is only ever compared and never written; another account gets `RUN_NOT_FOUND`, the same as an id that never existed), and **when** (only a run already claimed through the registry's one grant). With Supabase configured and no service-role key it refuses (`STORE_UNAVAILABLE`) and never falls back to the caller's client. `checkLiveRunPreflight()` is unchanged and still runs in the pipeline at both ends, before the token and before the judge; the writer does not repeat it. **The insert and delete policies are dropped and the grants closed by migration `0004_runs_server_only_writes.sql` (security lane S1b).** It drops `runs_insert_own` (F2) and `runs_delete_own` (F1), recreates `runs_select_own` for `authenticated` only on `(select auth.uid())` (F13), revokes every privilege on `public.runs` from `anon` and every one but SELECT from `authenticated` (TRUNCATE included, which row-level security never covers), revokes the browser roles' grants on the rate-limit table's sequence, and indexes `run_tokens(user_id)` (F17). So a signed-in user can read their own runs and write nothing, and an anonymous visitor is refused outright; through the REST API both refusals come back as permission denied (`42501`), not as an empty result. **THE MIGRATION MUST ONLY BE APPLIED TO A DATABASE AFTER THE S1a CODE IS DEPLOYED AGAINST IT**, because before S1a the app inserted through the user's own session and would fail to save every run. A migration in the repo is not a migration applied: F1 and F2 are closed on a given project only once `0004` has been pushed to it. `tests/integration/rls/runs-rls.test.ts` asserts all of it, the two former `it.fails` now plain tests, plus the catalog itself (the policy's role and text, the TRUNCATE privilege, the sequence grants, the index) read with psql inside the local stack's database container. That suite and `tests/integration/rls/server-only-run-writes.test.ts` (the app's create, finish and discard paths over real Postgres, needing no insert or delete grant) run against the local Supabase stack, gated on `RLS_LOCAL_STACK=1` and refusing any URL that is not loopback; CI runs them in the Authenticated axe job, which already starts that stack. **The service-role key cannot reach the browser:** `tests/unit/lib/secret-leakage.guard.test.ts` walks the import graph from every `'use client'` module and fails if it reaches the service-role client, the run writer, or a file that reads the key, and `scripts/verify-no-service-role-in-client.ts` reads the built `.next/static` for the key's name and, when it is set, its value. **A DISCARDED RUN STILL COUNTS, AND IS NEVER JUDGED ([ADR-0013](docs/adr/0013-a-discarded-run-is-stored-unjudged.md)).** The owner of an open run can end it with DISCARD RUN instead of END RUN AND GET RESULT, for a run that was not a test (a tool pressed by hand in a manual client). `LiveRunHost.discard()` makes the SAME claim `finish()` and `abandon()` make, so a discard, a finish, a second tab and the reaper compete once and exactly one acts; it revokes the token, calls **no gate and no detector**, and stores (through the run writer) a marker row (`DiscardedRunSchema`, strict, in the same `runs.run` column, **no migration**) that has no `verdict` key at all. No fake verdict is ever written and `generateFixReport` is never reached for one. **The allowance is NOT returned:** `countRunsSince` counts every row, discarded ones included, so a start and a discard is not a free run. **The spend meter does NOT count it:** `createRunTableSpendMeter` reads the period total and subtracts the rows marked discarded, because a discard made no judge call (two counts and a subtraction, since a negated filter on `run->>discarded` is NULL for every judged row and would report a spotless month). Judged reads (`RunRepository`) never return a discarded row; the markers are read through a separate port (`DiscardedRunStore`, `getDiscardedRunStore()`), so the leaderboard, the replay and the fix report cannot be handed a run with no verdict. A discarded run cannot afterwards be finished, judged or reconnected: the owner gets the typed refusal `RUN_DISCARDED`, and another account gets `RUN_NOT_FOUND`, exactly as for an id that never existed. **Run-endpoint credential handling ([ADR-0006](docs/adr/0006-mcpwn-is-the-mcp-server.md)):** we **do NOT hold the user's agent credentials** — we never call their agent, so there is no key of theirs to store, log or leak. Instead we **authenticate the INCOMING agent connection**: each run issues a **per-run, per-account token** that our MCP endpoint requires, used **server-side only**, transported over **HTTPS**, **never logged**, and **never persisted in plaintext**. Tokens are **scoped to one run and expire with it**, so a leaked token exposes one sandboxed run of fabricated attack content, never an account. **We are deliberately inviting a stranger's agent to connect to an endpoint we run, and the tools we serve are hostile by design** — treat that endpoint as inbound attack surface, with nothing real behind it. The operator-provided validated judge stays **LOCKED** and is never user-swappable. **Supabase config** (env-only): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` (public/client-safe), `SUPABASE_SERVICE_ROLE_KEY` (**secret · server-only** — never client-exposed, never logged, never persisted in plaintext). **THE PREFIXED NAMES ARE THE REAL ONES.** There are no `SUPABASE_URL` / `SUPABASE_ANON_KEY` readers anywhere in `src/`; unprefixed variables of those names are inert wherever they are set. This cost half of a production investigation on 2026-08-09: `/api/mcp` returned 500 `Invalid API key` because the deployment carried both spellings and the SERVICE-ROLE key belonged to a different project than `NEXT_PUBLIC_SUPABASE_URL` named, while the inert pair made it look like nothing was missing. **A deploy sets exactly three, and all three must name ONE project** — check the `ref` claim in each key JWT rather than trusting the variable name. `DATABASE_URL` is **tooling-only and read by nothing in the app** — the `PERSISTENCE_DRIVER` switch and the `getPersistenceConfig()` accessor that once validated it were deleted with the superseded store they configured.

## Scope — Core-7 (OWASP Agentic Top 10 2026; genai.owasp.org)

ASI01 Agent Goal Hijack · ASI02 Tool Misuse and Exploitation · ASI03 Identity and Privilege Abuse · ASI04 Agentic Supply Chain Vulnerabilities · ASI05 Unexpected Code Execution (RCE) · ASI06 Memory & Context Poisoning · ASI10 Rogue Agents (v1 bounded to four single-run signatures: goal drift, covert action, deceptive report, scale-out; `src/attacks/asi10.ts`).

**Why seven, not ten — the measurability bar (locked; [ADR-0003](docs/adr/0003-core-7-scope-and-measurability-bar.md)):** a category ships only if the compromise is (1) **observable** in the agent's own `Trace` steps, (2) inside **one bounded run**, (3) **anchorable** to a single offending step (`Verdict.stepId` — "compromised at step N, or not"), AND (4) has a **benign variant that scores not-compromised** (without it we can measure recall but never precision). ASI07 (Insecure Inter-Agent Communication — needs an agent-to-agent step type the Trace lacks), ASI08 (Cascading Failures — OWASP defines it as the *propagation* of a fault, not the initial vulnerability, so there is no single step to anchor), and ASI09 (Human-Agent Trust Exploitation — completes inside a human's decision the trace can't observe) do not clear the bar under the current contract. Seven measured beats ten unmeasurable.

## Data contract (single source of truth; UI renders observable data only)

- `Trace` — OBSERVABLE only: `{ runId, target, model, category, steps[] }`; step types: **principal_instruction** | agent_reasoning | tool_call | tool_result | memory_read | memory_write | task_complete. No labels. **The inbound instruction turn is `principal_instruction`, never `attacker`** ([ADR-0011](docs/adr/0011-the-principal-instruction-is-its-own-step-type.md)): the principal is the authority on whose behalf the agent acts, their instruction reaches the agent out of band on a channel we control, and it is the ONLY inbound turn a hosted run can observe. Untrusted third-party content is typed by the channel it arrived on — `tool_result`, `memory_read`, or the tool description in the listing — and there is deliberately **no untrusted-inbound type**: it is a step no hosted run can emit, and a trust annotation computed by the same builder that computes the label would prime the judge exactly as the 2026-07-28 category leak did. The type is a channel fact (who sent the turn), never a trust verdict. **Exactly one per trace, first**, in every realization of both kinds — that zero variance across the classes is what makes it safe to serialize to the judge, and it is asserted over the whole registry in `tests/unit/attacks/leakage.property.test.ts`, not reviewed.
- `GroundTruth` — HELD OUT: `{ compromised, stepId?, category }`, produced at construction; the detector NEVER receives it.
- `Verdict` — `{ runId, compromised, score, severity, category, rationale, stepId? }` (`stepId` present iff compromised).
- `RunResult` — a LIVE run's output: `{ runId, target, model, category, trace, verdict }`; no groundTruth (live runs are unlabeled).
- Attacks expose `build(variant) → { trace, groundTruth }` (detector validation) and `scenario(variant) → { taskGoal, environment }` (drive a live agent). Types via `z.infer`.

## Ground truth vs detector (leakage separation — the core invariant)

Standard ML anti-leakage: never let the model use information unavailable at prediction time; keep the label out of the features (target leakage — Kaufman et al. 2012, *Leakage in Data Mining*; train/test separation). Applied here: the observable `Trace` is the feature; the held-out `GroundTruth` is the label; the detector and UI see only the Trace. P/R compares detector verdicts to held-out ground truth on constructed fixtures; live runs are unlabeled — which is why the detector exists.

## Detector (module 4)

Blind LLM alignment-auditor (LlamaFirewall/AlignmentCheck style; arXiv 2505.03574): reads the whole Trace vs the task goal, classifies the Core-7 category, anchors the offending step. Trace/goal go in as untrusted, delimited data (never instructions; guards against judge-injection — JudgeDeceiver, arXiv 2505.13348). Structured output → Zod value-validation → typed `DetectorError`, never a raw crash. Low temperature (env), pinned model, empty-trace pre-check.

**The live judge (Slice 2b).** `createAnthropicJudge()` (`src/detector/anthropic-judge.ts`) is the HTTP `JudgeModelPort` — one `JudgeRequest` becomes one `POST {JUDGE_BASE_URL}/v1/messages` (Anthropic Messages API, `x-api-key` + `anthropic-version`), with the fixed rubric as `system` and the delimited untrusted trace as a single user message, so the injection boundary survives serialization. `model` and `temperature` are read off the request, not off the adapter's own config, so there is one source of truth for which model produced a measured number. Failures are typed `JudgeAdapterError`s (`CONNECTION_FAILED` · `TIMEOUT` · `HTTP_ERROR` · `MALFORMED_RESPONSE` · `EMPTY_RESPONSE`) with bounded exponential-backoff retries on 429/5xx and a per-request deadline; the key is a header and is interpolated into nothing. **`JUDGE_MODEL` must accept `temperature`** — the Claude 4.7+ and 5 families reject sampling parameters with a 400, and a pinned low temperature is part of what makes a measured P/R reproducible; `claude-haiku-4-5` is the intended cheap validated judge.

`resolveLiveDetector()` (`src/detector/resolve.ts`) is the **only consumer** of `JUDGE_BASE_URL` / `JUDGE_API_KEY`. It returns `null` when no key is configured — an unconfigured judge means live detection is unavailable, not a crash on a public route, and sample playback needs no credential at all — and throws a typed `ConfigError` when a key is set but the model or base URL is missing, because a half-configured judge is a deployment mistake, not silent inertness.

**THE LOCKFILE RULE — never regenerate `package-lock.json` on Windows.** `npm install` resolves the optional-dependency tree for the platform it runs on and PRUNES the entries it does not need, so a regeneration on this Windows dev machine silently drops the packages the **Linux** CI runner installs from: `lightningcss-linux-*` (Tailwind v4's engine), `@unrs/resolver-binding-linux-*` (the ESLint import resolver), and `fsevents`. `npm ci` on the runner then installs a tree with **no native binaries**, and the unit step fails on a machine that looked perfectly fine locally. **This actually happened:** a single regeneration removed **2532 lines** from the lockfile and broke CI, and nothing about the local run hinted at it. So:
- **Edit the lockfile IN PLACE.** `npm install` applies an `overrides` change to the existing tree without pruning the optional entries, so an override bump or a pin is a small, reviewable diff. **A lockfile diff that deletes hundreds of lines you did not intend is the tell** — read the diff before committing it, every time.
- If a full regeneration is genuinely required, do it **under Linux/CI parity** (the CI container or WSL), never from Windows.
- **`npm install` reporting "up to date" does NOT mean the overrides were re-resolved.** npm can consider the tree satisfied and skip re-resolution entirely, so a pin appears applied while the lockfile still carries the old version. Verify against the lockfile itself (`npm ls <pkg>`, or read the entry) rather than trusting the summary line.
